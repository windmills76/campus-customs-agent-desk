The cause is that approvals execute during a run, and the final decision overwrites the ticket status without reading it again. The same thing happened on 103 with approval #6 (approved 13:29:32, decision recorded 13:29:42 as awaiting approval). Both times the board was wrong for about a minute, and the next run had to fix it.

Evidence: 101 tab, Actual run 2 (approval #4 and the 13:18:01 decision); 103 tab, Actual run G (approval #6 and the 13:29:42 decision).

Two smaller points. Inventory asked Accounting for the purchase order directly, instead of going through Boss. That was allowed by the tools, but it wasn't in the plan. And because the approval landed mid-run, the team never recorded the "waiting on stock" state I expected, so the run went straight from ordering to fulfilling.

Evidence: 101 tab, Actual runs 2 and 3.

4. Could one agent with tools do this more simply?

Yes, for this workload. Each ticket here is a short sequence: check stock, check the vendor, request money or an order, wait for a person. None of the steps needed two minds. A single agent with the same tools and the same approval gates would have been simpler, cheaper, and probably faster, because it wouldn't have needed the handoffs that created most of the repeated runs on 103.

The split still earned something, but less than it looks. The main gain is authority: only accounting can request money, only customer service can draft, and inventory can't touch cash. Those limits are enforced by tool lists, and a single agent could have the same limits by tool access. The second gain is an audit trail with a name on each step, which is useful for this exercise. The cost was the delegation overhead: 103 made 17 delegations across nine runs (15 from Boss, 2 from Inventory to Accounting). If I rebuilt this, I'd keep a separate accounting role, because it's the only one that touches money, and fold inventory and facilities into one operations agent.
